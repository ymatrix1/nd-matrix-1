# Releasing

How to cut `vX.Y.Z`. The pipeline is `.github/workflows/release.yml`; packaging and checks are
`tools/release_package.py` and `tools/release_verify.py` (unit-tested under `tools/tests/`).

## What a release contains

Each platform ships a portable archive plus native OS installers (all with `.sha256` sidecars and a combined `SHA256SUMS.txt` on the release page):

| Platform | Runner | Target triple | Artifacts |
|---|---|---|---|
| Linux x86_64 | `ubuntu-22.04` | `x86_64-unknown-linux-gnu` | `nd-matrix-1-vX.Y.Z-linux-x86_64.tar.gz`, `nd-matrix-1-X.Y.Z-x86_64.AppImage`, `nd-matrix-1_X.Y.Z_amd64.deb` |
| Windows x86_64 | `windows-latest` | `x86_64-pc-windows-msvc` | `nd-matrix-1-vX.Y.Z-windows-x86_64.zip`, `-setup.exe` (Inno Setup) |
| macOS Apple silicon | `macos-latest` | `aarch64-apple-darwin` | `nd-matrix-1-vX.Y.Z-macos-arm64.tar.gz`, `.dmg`, `.pkg` |

Every portable archive and native installer packages `ns4`, `nd-matrix-1`, `nd-matrix-1-standalone`,
`nd-matrix-1.clap`, `nd-matrix-1.vst3`, `README.txt` (install paths per OS, source:
[RELEASE_README.txt](RELEASE_README.txt)), `HOST_COMPATIBILITY.md`, `ADDITIONAL-PERMISSIONS.md` and `TRADEMARKS.md` ([D241](DECISIONS.md#d241-licensor-additional-permission-for-musicians-and-a-trademark-policy-ship-as-separate-files); a release without them fails), `THIRD_PARTY_LICENSES.html` (copyright and license texts of every third-party crate, [D238](DECISIONS.md#d237-releases-ship-third-party-license-notices-generated-by-cargo-about)), and any `LICENSE*` files in the repo root.
The notices sit next to `LICENSE`: archive root, Inno `{app}`, `.deb` and AppImage `usr/share/doc/nd-matrix-1/`, `.dmg` root, `.pkg` `/usr/local/share/doc/nd-matrix-1/` and the installer resources.
Linux additionally ships `licenses/appimage-runtime/` (license texts and sources of the runtime inside the `.AppImage`: type2-runtime, musl, LGPL-2.1 libfuse, squashfuse, zstd, zlib, mimalloc; [D242](DECISIONS.md#d242-the-appimage-runtime-is-pinned-and-its-notices-ship-with-the-linux-release)) in the archive and under `usr/share/doc/nd-matrix-1/appimage-runtime/` in the AppImage. `tools/release_verify.py` fails a Linux archive without it.
The LGPL-2.1 libfuse inside the runtime also requires its source: Linux releases carry `nd-matrix-1-vX.Y.Z-appimage-runtime-sources.tar.gz` (+ `.sha256`) beside the archives, built by `tools/release_runtime_sources.py`, and `release_verify.py` fails a Linux archive without it.
Native installers are generated by `tools/release_installers.py` (unit-tested in
`tools/tests/test_release_installers.py`) and install or let the user select the CLAP and VST3 plugins
into the OS plugin folders. Intel macOS and Linux arm64 are not built.

Plugin layout inside the archive:

| OS | CLAP | VST3 module |
|---|---|---|
| Windows | `nd-matrix-1.clap` (a DLL) | `nd-matrix-1.vst3/Contents/x86_64-win/nd-matrix-1.vst3` |
| Linux | `nd-matrix-1.clap` (a shared object) | `nd-matrix-1.vst3/Contents/x86_64-linux/nd-matrix-1.so` |
| macOS | `nd-matrix-1.clap/Contents/{Info.plist,MacOS/nd-matrix-1}` | `nd-matrix-1.vst3/Contents/{Info.plist,MacOS/nd-matrix-1}` |

The bundle name comes from `bundler.toml` (`[nord-plugin] name = "nd-matrix-1"`), not from the crate
name; `PLUGIN_STEM` in `tools/release_package.py` must equal it (a test pins this). Host identity
(`CLAP_ID`, `VST3_CLASS_ID`, plugin `NAME`, parameter IDs) does not depend on the file name.

Releases before this rename shipped `nord-plugin.clap` / `nord-plugin.vst3`. Upgrade handling:

| Installer | Legacy bundle removal |
|---|---|
| Windows (Inno Setup) | `[InstallDelete]` entries for the CLAP and VST3 folders under `{commoncf64}`, per selected component |
| macOS `.pkg` | `preinstall` script in the `vst3` and `clap` component packages removes the legacy bundle under `/Library/Audio/Plug-Ins` |
| Linux `.deb` | dpkg removes files the old package version owned; nothing extra needed |
| Linux AppImage | `AppRun --install-plugins` deletes the legacy files in `~/.clap` and `~/.vst3` before copying |
| `.dmg`, portable archives | manual copy; `RELEASE_README.txt` tells users to delete the old `nord-plugin.*` |

The standalone plugin host binary was `nord-plugin-standalone` and is now `nd-matrix-1-standalone` (`ns4-b9rn`; the Cargo `[[bin]]` name in `crates/nord-plugin/Cargo.toml`, `STANDALONE_BIN` in `tools/release_package.py`). The Windows installer deletes the old `{app}
ord-plugin-standalone.exe`; `.deb` upgrades drop it through dpkg; the macOS `.pkg` and portable archives leave a stale copy in place that users delete by hand.
`tools/release_verify.py` fails any archive whose name, top folder, or any shipped file, folder or bundle starts with the vendor trademark `nord-` (`ns4-9wq1`).

Builds are unsigned (no Authenticode, no Apple notarization). The macOS README explains `xattr -dr com.apple.quarantine`.
The plugin is not verified in any DAW; every archive README and the release body say so. Remove that wording only
after [HOST_COMPATIBILITY.md](HOST_COMPATIBILITY.md) records real host tests.

## Automated path (preferred)

1. Actions, **Prepare release**, Run workflow, enter the version (`0.1.6`, no `v`). It runs `tools/bump_version.py`, refreshes `Cargo.lock` (`cargo update --workspace`, no system libraries needed) and `uv.lock`, and opens the release PR.
2. On the PR branch run Actions, **Release**, Run workflow, tag empty (dry run) and inspect the artifacts.
3. Merge after CI is green, then tag and push (see Cut the release). The `verify-published` job then downloads the published assets, checks `SHA256SUMS.txt` and the asset list.
4. Release notes are grouped by PR label via `.github/release.yml` (`enhancement`, `bug`, `documentation`, `skip-changelog`).

Locally the same bump is `python tools/bump_version.py X.Y.Z` (`--no-lock` edits files only). The manual table below is what it changes.

## Version bump locations

The version lives in two places. Change both in the release PR; nothing else needs editing.

| File | Field | Notes |
|---|---|---|
| `Cargo.toml` | `[workspace.package] version` | Every crate uses `version.workspace = true`; `ns4 info` and the plugin report it via `CARGO_PKG_VERSION` |
| `pyproject.toml` + `uv.lock` | `[project] version` (run `uv lock`) | Python tooling only; a unit test fails if it differs from `Cargo.toml` |

Then run `cargo check --workspace` so `Cargo.lock` picks up the new version, and commit the lock file with the bump.
The tag must equal `v` plus the `Cargo.toml` version (`v0.2.0` for `0.2.0`, `v0.2.0-rc.1` for `0.2.0-rc.1`).
The workflow fails in its first job if they differ, before any build minutes are spent.
A tag with a hyphen is published as a GitHub pre-release.

## Pre-release checklist

- [ ] Version bumped in both files above, `Cargo.lock` updated, merged to `main` through a PR.
- [ ] CI is green on that exact `main` commit (all three OS, Python job). The release workflow does not repeat the test suite; CI also runs on `v*` tags, so the tagged commit gets a second full result.
- [ ] Checks from `AGENTS.md` pass locally if the bump touched anything besides the version.
- [ ] `python tools/check_licenses.py` passes (CI job `licenses`): no copyleft crate in the shipped `nord-plugin` tree, so the binaries can be distributed under PolyForm Noncommercial 1.0.0. The VST3 wrapper uses the MIT or Apache-2.0 `vst3` crate; bundling needs no extra tool (`cargo xtask bundle` as before, no libclang or VST3 SDK).
- [ ] Dry run is green (next section) and the artifacts were downloaded and inspected at least once for this release.
- [ ] `docs/HOST_COMPATIBILITY.md` is current. If a DAW test result changed, update the README wording in `RELEASE_README.txt`.
- [ ] No `.reference/`, firmware, backup or preset files are staged (`git status`, and `tools/release_verify.py` enforces it for archives), and embedded firmware data (`fw-data-inventory`, e.g. `vox_image.rs`, `synth-p-words.csv`) has been migrated to runtime loading before tagging a public release.
- [ ] CI job `third-party-notices` is green: every crate license is in `about.toml` `accepted`. A new license needs a review of its terms first (add it to `accepted` in the PR that adds the dependency).
- [ ] `ADDITIONAL-PERMISSIONS.md` and `TRADEMARKS.md` exist in the repo root (`python tools/license_check.py` tests pin their key phrases).
- [ ] `LICENSE` file(s) exist in the repo root; `tools/release_package.py` includes any `LICENSE*` it finds.

## Third-party license notices

`THIRD_PARTY_LICENSES.html` is generated, not committed (git-ignored). `release.yml` does it in each build job before packaging.
Locally, run it from the repo root before `release_package.py` (which stops and prints the command if the file is missing):

```bash
cargo install --locked cargo-about@0.8.4   # once; keep equal to CARGO_ABOUT_VERSION in release.yml and ci.yml
cargo about generate --locked --fail --workspace --all-features -c about.toml about.hbs -o THIRD_PARTY_LICENSES.html
```

It takes about one minute and needs the crates downloaded (`cargo fetch`). `about.toml` lists the three shipped targets,
so any OS produces the same file. The run fails on a license outside `accepted` or a missing license text. A log line
`failed to parse license 'GPL-3.0'` comes from a low-confidence source scan of the `nih-plug` checkout (plugins we do not build),
not from a crate license, and does not change the output or the exit code.

## Dry run (publishes nothing)

GitHub: Actions, Release, Run workflow, branch `main`, leave **tag empty**. This builds all three platforms, packages,
runs `release_verify.py`, and uploads the archives as workflow artifacts (14 days). The `publish` job is skipped.
Dry-run archives are named `...-vX.Y.Z-dev-<platform>...`, so they cannot be mistaken for a release.

Locally (any OS, after the build steps in the workflow):

```bash
T=x86_64-pc-windows-msvc   # your host triple from the table above
cargo build --release --locked --target $T -p nord-core --bin ns4
cargo build --release --locked --target $T -p nord-gui --bin nd-matrix-1
cargo build --release --locked --target $T -p nord-plugin --bin nd-matrix-1-standalone
cargo xtask bundle nord-plugin --release --locked --target $T
cargo about generate --locked --fail --workspace --all-features -c about.toml about.hbs -o THIRD_PARTY_LICENSES.html
python tools/release_package.py --target $T
python tools/release_verify.py dist/nd-matrix-1-*.zip --target $T
```

`cargo xtask bundle` locates the workspace root as the outermost ancestor directory containing a `Cargo.toml`.
Run it from a checkout that is not nested inside another Cargo workspace (for example a git worktree under the repository),
or it builds the outer checkout instead.

## Cut the release

1. Merge the bump PR. Wait for CI on `main`.
2. Tag the merge commit and push the tag (this is the only step that publishes):
   ```bash
   git switch main && git pull --ff-only
   git tag -a vX.Y.Z -m "vX.Y.Z"
   git push origin vX.Y.Z
   ```
3. The `Release` workflow runs: `plan` (tag format, tag exists, tag equals `Cargo.toml` version) then `build` x3
   (build, CLI smoke test, package, verify, upload) then `publish` (combine and check `SHA256SUMS.txt`, create the release).
4. Open the release page and read the body. Release notes are generated by GitHub from merged PRs since the previous tag,
   below a fixed header that states the plugin is not DAW-verified and the builds are unsigned. Edit the notes there if needed.

To re-publish an existing tag (for example after a failed run): Actions, Release, Run workflow, enter the tag. The workflow
checks out that tag, not the branch, and refuses a tag that does not exist (it never creates one).
To drop a bad release: delete the release and tag on GitHub (`gh release delete vX.Y.Z --cleanup-tag`), fix, bump, retag.
Never move a published tag.

## Verify a download (checksums)

Put the archive and its `.sha256` file in one folder, then:

```bash
sha256sum -c nd-matrix-1-vX.Y.Z-linux-x86_64.tar.gz.sha256     # Linux
shasum -a 256 -c nd-matrix-1-vX.Y.Z-macos-arm64.tar.gz.sha256  # macOS
# Windows PowerShell: compare the printed hash with the line in the .sha256 file
(Get-FileHash .
ord-stage-4-emulator-vX.Y.Z-windows-x86_64.zip -Algorithm SHA256).Hash
```

`SHA256SUMS.txt` on the release page holds the same three lines.
The `.sha256` files and `SHA256SUMS.txt` are LF-terminated, two-space `sha256sum` format; the verifier rejects CRLF.
Checksums protect against corruption, not against a compromised release: there is no signature yet.

## What the pipeline checks

`tools/release_verify.py` fails the build when any of these is false:

| Check | Detail |
|---|---|
| One top folder, expected files only present | Includes the VST3 module at its per-OS path |
| Nothing forbidden | No `.reference`, `references`, `factory_programs`, `target`, `.git`, `.beans`, `.agents`, `.claude` path part; no `.ns4*`, `.nsmp4`, `.npno`, `.pdf`, `.bin`, `.fw`, `.ldr`, `.dxe`, `.hex`, `.asm`, `.pyc`, `.pdb` file |
| Allowlist packaging | `release_package.py` reads only the named binaries, the two plugin bundles, the README, `HOST_COMPATIBILITY.md`, `ADDITIONAL-PERMISSIONS.md`, `TRADEMARKS.md`, `THIRD_PARTY_LICENSES.html` and `LICENSE*`; stray files in `target/` or the repo are never read |
| No manufacturer name | Case-exact `Clavia` / `CLAVIA` absent from the CLI, GUI, standalone and plugin binaries |
| Plugin entry points | PE export table parse on Windows (`clap_entry`, `GetPluginFactory`); symbol-name search in the ELF/Mach-O image on Linux and macOS |
| Legal notices | `ADDITIONAL-PERMISSIONS.md` and `TRADEMARKS.md` present in the archive (D241) |
| Third-party notices | `THIRD_PARTY_LICENSES.html` present, at least 1 KB, contains `MIT License` and `Apache License` (D238) |
| README disclaimer | `README.txt` must say the plugin has not been verified in any DAW |
| Checksum file | Matches the archive, LF line endings |

Not checked by the pipeline: that a DAW loads the plugin, audio output, GUI start-up, macOS code signing, glibc floor of the Linux build
(built on `ubuntu-24.04`, so it needs glibc 2.39 or newer).

## Cost per run

Dry run or release: 3 build jobs (Linux, Windows, macOS) plus two small ubuntu jobs. The full test suite is not rerun
(the earlier workflow compiled and ran it in release mode on all three OSes). Rust cache is restored but not saved.

## Updating the AppImage runtime

`appimagetool` 1.9.0 downloads the moving `continuous` runtime unless told otherwise, so the release pins one (D242): `release.yml` downloads `runtime-x86_64` from a type2-runtime release tag and `tools/release_installers.py --appimage-runtime` checks it against `APPIMAGE_RUNTIME_SHA256` in `tools/release_package.py`. To bump it:

1. Pick a release tag at https://github.com/AppImage/type2-runtime/releases and download `runtime-x86_64`.
2. Read its `LICENSE`, `src/runtime/Makefile` and `scripts/common/install-dependencies.sh` for added or changed libraries, and run `strings` on the binary for the versions.
3. Update the pins in `tools/release_runtime_sources.py` (libfuse and squashfuse versions and sha256 from the new `scripts/common/install-dependencies.sh`, runtime tag and commit) and `licenses/appimage-runtime/` (texts and the README table), `APPIMAGE_RUNTIME_URL` and `APPIMAGE_RUNTIME_SHA256`, the URL in `release.yml`, and `docs/LEGAL.md` section 4.
4. Run `uv run pytest tools/tests/test_release_package.py` (it checks the README names the pinned tag and sha256, and that `release.yml` uses the pinned URL).

## AppImage on a bare host

The catalog (appimage.github.io) runs the AppImage on the oldest supported Ubuntu LTS, with no network and no extra packages ([D248](DECISIONS.md#d248-the-linux-appimage-is-built-on-the-oldest-supported-lts-bundles-the-xkbcommon-libraries-and-follows-the-catalog-file-name)). That is why the Linux job builds on `ubuntu-22.04` (glibc is only as old as the build system) and bundles `libxkbcommon`, `libxkbcommon-x11` and `libxcb-xkb` with their notices. Before a release, check on a bare Ubuntu 22.04 (container or VM, with `xvfb`):

```bash
chmod +x nd-matrix-1-X.Y.Z-x86_64.AppImage
xvfb-run -a ./nd-matrix-1-X.Y.Z-x86_64.AppImage   # must stay up for 10 s without "could not be loaded"
```

After a fix is released, comment `/retest` on the catalog pull request. Bump the runner when Ubuntu 22.04 leaves standard support (April 2027).
