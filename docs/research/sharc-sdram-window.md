# The external delay-line window of the FX, PNO and ORG chips

- **Checked:** 2026-11-24
- **Sources (local, never committed):** `target/DSP/dsp_image_0_FX.bin` through `python tools/ns4_dsp_ldr.py` (block listing and `--sram` images), the oracle runs `sharc-fxlive` and `tools/fx_oracle_live.py reverb0`; committed: [dsp-image-hunt](dsp-image-hunt.md) s5.18, [fx-reverb-leslie](fx-reverb-leslie.md) s11, [sharc-chip-identity](sharc-chip-identity.md); code `crates/nord-sharc/src/core/sdram.rs`, `core/memory.rs`.
- **Question:** what is the `0x20xxxxxx` window of the loader streams (bean `ns4-lle4`, `ns4-8aoy`), where do the delay and reverb lines of the FX program sit in the data address space, and what does the core model need to serve them?

## 1. Short answer

| Item | Result | Tag |
|---|---|---|
| Address mapping | normal-word address `w` in `0x0800_0000..0x0804_0000` is loader byte address `0x2000_0000 + 4 * (w - 0x0800_0000)` | VERIFIED (two exact matches below) |
| FX Core1 lines | 5 lines x `0x5000` words at `w = 0x0800_4000 + 0x5000 k`, loader zero block `0x2001_0000..0x2007_4000`, 409,600 B | VERIFIED (loader listing, reverb instance pointers) |
| FX Core2 lines | same shape at `w = 0x0802_0000 + 0x5000 k`, loader zero block `0x2008_0000..0x200E_4000`, 409,600 B | VERIFIED |
| What the window is | the loader calls it `0x20xxxxxx` (L2 of an ADSP-2157x); the FX code reaches it through the 32-bit data address `0x08xxxxxx`. The physical part (L2, SDRAM bank, other) is not identified; the firmware sees plain memory | ASSUMED (plain memory) |
| Model | dense 1 MiB word store `core/sdram.rs`, allocated on first write, always on (no flag), own counters `sdram_reads` / `sdram_writes`; the previous sparse device map served the same addresses with the same values | tests + run |
| Effect on audio | none: `reverb0` against `FwReverb`, 1.5 s burst, null depth after gain fit **-129.2354 dB** before and after (the same figures to 4 decimals), 102,000 reads and 112,016 writes of the window per run | VERIFIED (run) |

## 2. Method

1. `python tools/ns4_dsp_ldr.py DSP/dsp_image_0_FX.bin` lists, per core section, the `0x20xxxxxx` blocks: Core1 one 844 B data block at `0x2000_4000` (the DMA descriptor rings, `sharc-chip-identity.md`) and one zero block of 409,600 B ending at `0x2007_4000`; Core2 one zero block of 409,600 B `0x2008_0000..0x200E_4000`.
2. The reverb instance of [fx-reverb-leslie](fx-reverb-leslie.md) s11 holds the line bases as data words (`0x0800_4000 + 0x5000 k` Core1, `0x0802_0000 + 0x5000 k` Core2, length `0x5000`). Five lines of `0x5000` words are 409,600 B.
3. With a factor 4 between a word address and the loader byte address, the Core2 base `0x0802_0000` lands on `0x2008_0000` (the start of the Core2 block) and the Core1 base `0x0800_4000` on `0x2001_0000` (the end of the block minus 409,600). Both are exact, so the factor and the origin `0x0800_0000` are fixed by two independent points.
4. Run: `sharc-fxlive IMAGE --core 1 --passes 17000 --in-wav burst.wav --script-flat reverb0.script` (generated by `tools/fx_oracle_live.py reverb0`) prints `sdram window 0x08000000: 102000 reads, 112016 writes`; the comparison output of `tools/fx_oracle_live.py reverb0` is identical to the one of the build with the sparse store.

## 3. What is not modelled

- Latency, bus contention, refresh and the L2 versus external ordering (the sharc oracle runs one access per instruction).
- The 0x0800_0000 window of the **SY1SY2 and SMP** chips is the AMI bank 2 address latch of the flash path ([sy-flash-bus-hunt](sy-flash-bus-hunt.md)), which `EpChain` / `SmpFlash` serve before the core memory is reached. Those chips keep their behaviour: the models run first, and without them the window is the same plain memory as before.
- Loader blocks with data (a non-zero `0x20xxxxxx` block): `Sdram::load` exists for it, no FX block needs it. The Core1 descriptor block at `0x2000_4000` is the SC57x L2 (`--sc57x`, `periph/l2.rs`, byte addressed), not this window.

## Implications

- Delay and reverb lines work in the oracle on a dense store; the open point "SDRAM mapping" of `dsp-image-hunt.md` s5.18 is closed as a mapping, the physical device stays open and does not affect the audio.
- The dense store makes a pass that streams 400 KB of delay lines cheaper than the sparse map (no hashing); not measured here.

## Follow-ups

1. Identify the part (L2 or an external bank) if a timing model is ever needed (latency is invisible to the audio).
2. Feed non-zero loader blocks of `0x20xxxxxx` through `Sdram::load` when an image needs them.
