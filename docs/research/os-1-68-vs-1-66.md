# OS v1.68 against v1.66

- **Checked:** 2026-11-27
- **Sources:** local file `.reference/Update Nord Stage 4 OS v1.68.zip` (7,213,093 B, sha256 `f5c82273869e615cc9ae346bcdd906a80d27aad47c8c4097de5fd354b0be39e7`, not committed); the v1.66 files unpacked earlier (`target/fw_unpacked/`); the v1.44 to v1.64 zips; `tools/fw_addr_map.py`, `tools/ns4_dsp_images.py`, `tools/ns4_dsp_ldr.py`, `ns4 inspect`, `ns4 firmware info`, `arm-lle-bench`, `sharc_jit_diff`; [os-update-input](os-update-input.md), [arm0-rust-runtime](arm0-rust-runtime.md)
- **Question:** what changed between the OS v1.66 and v1.68 images, and which tool, parser or test path of the project depends on the v1.66 layout?

Only sizes, hashes of the local files, addresses and counts are recorded here; no firmware bytes (D20, D128).

## 1. Container

The zip holds one `Update Nord Stage 4 OS v1.68.exe` (12,770,944 B; v1.66: 12,770,968 B). The container sits at file offset `0x79C330` (v1.66: `0x79CB30`); the same header scan as v1.66 finds it (`0x20` header, `size0 + 0x20 == offset1`, total = `0x20 + size0 + size1`). `ns4 inspect --unpack` unpacks it unchanged (all six checksums `OK`).

| Item | v1.66 | v1.68 |
|---|---|---|
| Container bytes | 4,037,080 | 4,038,888 (+1,808) |
| fnv1a64 / sha256 prefix | `5fd75f195e3671be` / `5c4762411171c811` | `61eb4b85d225b702` / `6f7d06302552c6e2` |
| Image 0 / image 1 bytes | 3,575,686 / 461,362 | 3,577,494 / 461,362 |
| Image 0 sub-header version byte (`+0x21`) | `0xA6` | `0xA8` |

**Version field (VERIFIED, `ns4 inspect`, 9 containers):** the byte at container offset `0x21` is the OS version number: `0x90 0x92 0x98 0x9A 0xA0 0xA2 0xA4 0xA6 0xA8` = 144, 146, 152, 154, 160, 162, 164, 166, 168 for the v1.44 to v1.68 updates. `ns4 inspect` prints it as `OS version: N` (`firmware::os_version`).

## 3. `bank0_CODE`

Three regions (found with `tools/fw_addr_map.py` and word-level diffs; the local files only):

| Region (v1.66 offsets) | Change |
|---|---|
| ARM code `0x0..0x2A0000` | recompiled: about 88 % of the 8-word blocks are identical once branch offsets and address-like words are masked (86,015 sampled blocks, 10,155 unmatched); functions move by up to about 1.4 KB either way, so every ARM0 address of the harness changes |
| rodata `0x2A0000..0x2D8644` | non-pointer content identical except 14 small spots (about 500 words): a menu string added (s6), two debug strings gone, one 776 B table and two string blocks moved, a few vtable entries; shift grows from `+0x368` to `+0x3A0` |
| `0x2D8644` to the end of the DSP images `0x53AF58` | byte-identical, shifted by exactly **`+0x3A0`** (928 B) |

**DSP images (VERIFIED, `tools/ns4_dsp_images.py`, `tools/ns4_dsp_ldr.py --sram`):** the five images FX, PNO, ORG, SY1SY2, SMP have the same sizes (164,880 / 288,804 / 296,656 / 121,844 / 44,596 B) and **identical sha256 prefixes** (`4f952a03...`, `0a16af5c...`, `aea227e7...`, `f6ee7a09...`, `30aa3d65...`). They start `0x3A0` later (FX at `0x446A1C`, v1.66 `0x44667C`). The loader census (blocks, sections, entry values) is identical for FX, PNO and ORG, and the flat per-core SRAM images (`--sram`) are byte-identical for ORG. So every SHARC entry pc, census pc, force/idle pc and message script of `live_presets.rs` and the AOT benchmarks holds unchanged: the SHARC side did not change in v1.68.

## 4. What the v1.66 constants became

`tools/fw_addr_map.py OLD NEW addr...` maps an address by matching instruction windows with `B`/`BL` offsets and address words masked (code), and by following the `ldr rX, [pc, #n]` that loads a data address (data). Mapped addresses, in `crates/nord-arm/src/machine/layout.rs` (`Layout::V168`):

| Item | v1.66 | v1.68 |
|---|---|---|
| Flow control / `operator new` | `0xC006CA48` / `0xC025D56C` | `0xC006CA94` / `0xC025D8D4` |
| Application thunk / main loop | `0xC025D524` / `0xC00A0248` | `0xC025D88C` / `0xC00A029C` |
| Port object cell / comm table / AINTC table | `0xC055B150` / `0xC053F8A4` / `0xC055F674` | `0xC055B4F0` / `0xC053FC44` / `0xC055FA14` |
| Init array (4 entries) | `0xC00002A4`, `0xC024D1A0`, `0xC024DC64`, `0xC025DBBC` | `0xC00002A4`, `0xC024D508`, `0xC024DFCC`, `0xC025DF24` |
| WAVE registry record 0 | `0xC02FD4B0` | `0xC02FD850` (+0x3A0) |
| Font table / bar font | `0xC029E5AC` / `0xC02C3BA8` | `0xC029E914` (+0x368) / `0xC02C3F40` (+0x398) |

The two repeated static-init stubs (`0xC024D1A0`, `0xC024DC64`) are ambiguous by content; the mapper picks the copy where the neighbouring code moved to (support 0 in its output). The other harness addresses and data cells of `layout.rs` (27 addresses in all) map with unique 8-word to 64-word windows. The WAVE registry address found by the mapper equals the one found by the layout scan (two independent ways). The Bass `A` lines (53 ranges of ARM constants read by byte offset) are all found byte for byte in v1.68, each once: `+0x368` below `0x2B6000`, `+0x3A0` from `0x2D8644` (`dm_text::OS_V168`).

## 5. Parser and schema checks

- **Preset schema ids and sizes:** the literal-pool constants `0x139, 0xD0, 0xCB, 0xCD, 0x6C` (schema ids), `868, 195, 183, 124` (file sizes) occur the same number of times in both images (14, 14, 14, 11, 110; 1, 27, 15, 91). This is a count check, not a proof; it gives no sign of a new `CBIN` schema. Not run: a v1.68 `.ns4p` or `.ns4b` (none available; the Factory Restore archive is RevK v1.66).
- **WAVE registry:** 55 records, 605,164 samples, 46 WAVE tables: same totals as v1.66 (`tools/synth_wave_registry.py`).
- **Older updates:** with the registry scan, `ns4 firmware info` now reports 46 WAVE tables for the v1.44, 1.46, 1.52, 1.54, 1.60, 1.62 and 1.64 zips as well (they stopped at "registry record 0 has a foreign layout" before).

## 6. Visible feature change

One new menu choice string in the Piano `Dynamic Compression` list: `Soft+Treble`, placed before `Brilliant` (v1.66 starts the list at `Brilliant`). The list is the Clavinet-EQ mask names the project maps from `Edt_Pno_kEq` (`docs/specs/cbin-and-presets.md` s7). Whether the stored value range or the order of the other choices changed is open (OQ44). Two debug strings (`Osc Waveform Wave`, `Osc %s cat`) are gone; the `LAYER INIT` / rotor-angle strings moved.

## 8. Not verified

- No hardware or Unicorn run of v1.68 key and program paths; `arm-lle-bench` used the blank factory EEPROM image (`target/oled/eeprom.bin`), which gives no DSP traffic on key presses in v1.66 either, so program-load, key and edit message paths are not compared.
- The 27 Rust addresses are checked by the boot and by equal message counts, not one by one with a disassembler.
- The `bank0_SRAM` and 3 `ARM0` byte differences are unexplained.
- The `AOT` whole-pass benchmarks (`crates/nord-sharc` `aot_*`, `crates/nord-lle`) were not run: their inputs (the DSP images) are identical, so no change is expected; those files are owned by other sessions and untouched.

## Implications

- The DSP and SHARC work is unaffected by v1.68. Only the ARM side moves, and that is a pure recompile plus one menu string.
- A new OS update needs no code change where the code scans for a layout (WAVE registry, font table, bar font, DSP image chain). Where it reads fixed ARM addresses (`Layout`, the Bass `A` lines) it needs one new table, found with `tools/fw_addr_map.py`; unknown images keep the v1.66 layout and the Bass guard rejects them (`unsupported Nord OS version`).
- Decision: [D253](../DECISIONS.md). Open: [OQ44](../OPEN-QUESTIONS.md). Bean `ns4-c6kq`.
